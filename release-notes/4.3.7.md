## RabbitMQ 4.3.7

RabbitMQ `4.3.7` is a maintenance release in the `4.3.x` [release series](https://www.rabbitmq.com/release-information).

It is **strongly recommended** that you read [4.3.0 release notes](https://github.com/rabbitmq/rabbitmq-server/releases/tag/v4.3.0)
in detail if upgrading from a version prior to `4.3.0`.

### Minimum Supported Erlang Version

The minimum supported Erlang version for this release series is `27.0`.

[RabbitMQ and Erlang/OTP Compatibility Matrix](https://www.rabbitmq.com/docs/which-erlang) has more details on Erlang version requirements for RabbitMQ.

Nodes **will fail to start** on older Erlang releases.


## Changes Worth Mentioning

Release notes can be found on GitHub at [rabbitmq-server/release-notes](https://github.com/rabbitmq/rabbitmq-server/tree/v4.3.x/release-notes).

### Shovel Plugin

#### Bug Fixes

 * When the destination rejects a message, for example because the destination queue
   has `x-overflow` set to `reject-publish` and has reached its maximum length, the shovel
   now returns the message to the source queue as a failed delivery. A quorum source queue
   therefore dead-letters the message once it exceeds the [delivery limit](https://www.rabbitmq.com/docs/quorum-queues#poison-message-handling),
   instead of redelivering it to the shovel over and over (a regression in `4.3.0`).

   With an AMQP 1.0 source, such a message used to be dead-lettered on the first rejection.
   Now this happens once it exceeds the delivery limit. A classic source queue has no
   delivery limit, so the message is returned to it until the destination accepts it.

   GitHub issue: [#17794](https://github.com/rabbitmq/rabbitmq-server/pull/17794)

 * A shovel with an AMQP 1.0 destination did not settle a message at the source when
   the destination rejected or released it, and eventually stopped forwarding messages.

   GitHub issue: [#17794](https://github.com/rabbitmq/rabbitmq-server/pull/17794)

 * A shovel with an AMQP 1.0 source could restart and forward some messages twice when
   the destination confirmed messages out of order.

   GitHub issue: [#17794](https://github.com/rabbitmq/rabbitmq-server/pull/17794)

 * A shovel with an AMQP 1.0 source could settle messages incorrectly after more than
   4 billion deliveries. With a local destination, it could acknowledge a message at the
   source before the destination confirmed it.

   GitHub issue: [#17794](https://github.com/rabbitmq/rabbitmq-server/pull/17794)

### Erlang AMQP 0-9-1 Client

#### Enhancements

 * The `auth_mechanism` query parameter of an AMQP 0-9-1 URI is now restricted to
   the mechanisms the client actually supports (`plain`, `amqplain`, `external`,
   `crdemo`), and an unsupported value is now rejected when the URI is parsed
   rather than when the connection is established. This also applies to the
   Shovel and federation plugins, which parse URIs the same way.

 * Likewise, the `verify` query parameter of an AMQP 0-9-1 URI now only accepts
   `verify_peer` or `verify_none`, and an unsupported value is rejected when the
   URI is parsed rather than when the TLS connection is established.

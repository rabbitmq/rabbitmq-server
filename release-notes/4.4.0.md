## RabbitMQ 4.4.0

RabbitMQ `4.4.0` is a new feature release.

## Breaking Changes and Compatibility Notes

 * The following AMQP 0-9-1 headers are no longer parsed:

   ```
   x-amqp-1.0-properties
   x-amqp-1.0-app-properties
   x-amqp-1.0-message-annotations
   x-amqp-1.0-footer
   ```

   RabbitMQ 3.13 and earlier used them to carry the AMQP 1.0 sections of a
   message received over AMQP 1.0. Nothing has written them since 4.0, so only
   a message stored by a 3.13 or earlier node and not read since carries them.
   Such a message is still delivered, with these headers converted like any
   other `x-` header rather than restored as AMQP 1.0 sections.

 * Likewise, the `x-basic-delivery-mode`, `x-basic-priority` and
   `x-basic-expiration` message annotations are no longer parsed. They were
   written before 4.0 when an AMQP 0-9-1 message was encoded as AMQP 1.0 for a
   stream, so only a stream entry written by a 3.13 or earlier node carries
   them, and reading it no longer restores those three properties.

## Changes Worth Mentioning

### Core Server

#### Enhancements

 * The stream coordinator's Raft state machine advances to version 8. Its v7
   behaviour is frozen in a separate module (as already done for
   `rabbit_fifo`/`rabbit_fifo_v7`), so old log entries and mixed-version
   clusters replay against byte-identical code.

 * The state machine now owns member action retry backoff, replacing worker
   processes that blocked for the backoff window. Failed actions are parked
   and re-driven by a single coalesced timer, with a short jittered delay by
   default and node-down failures parked until the node's `nodeup` event,
   avoiding thundering herds and dead-node polling during mass disconnections.

 * The number of concurrently running action workers (start, stop, delete,
   update) is now bounded (default 64, configurable via
   `stream_coordinator_max_concurrent_actions`), avoiding an unbounded burst
   of workers during a mass stream event.

 * Node and connection reconnection handling in the stream and single active
   consumer coordinators now scales with the affected footprint rather than
   the total number of streams or groups, reducing coordinator load after a
   partition heals, a node restarts, or a rolling upgrade completes.

#### Bug Fixes

 * Fixed several stream coordinator liveness gaps: a stream could be left
   without a writer and no event to trigger recovery, a stale `start` action
   could survive a re-election, and a replica could stay disconnected instead
   of resuming on `nodeup`.

### Dependency Changes

 * `osiris` was upgraded to [`1.13.2`](https://github.com/rabbitmq/osiris/releases)
 * `ra` was upgraded to [`3.2.0`](https://github.com/rabbitmq/ra/releases)

## Breaking Changes and Compatibility Notes

### Classic Queues Evaluate Consumer Timeouts Again

RabbitMQ `4.3.0` moved consumer timeout handling into the queues themselves and, as part of that change, classic queues and streams stopped evaluating consumer timeouts (see the `4.3.0` release notes).

As of `4.4.0`, classic queues evaluate consumer timeouts again. When a consumer holds unacknowledged messages beyond the timeout, the messages are returned to the queue. For AMQP 1.0 clients, timed-out deliveries are released via `DISPOSITION(state=released)` instead of detaching the link, matching the behaviour introduced for quorum queues in `4.3.0`.

The timeout can be set via the `x-consumer-timeout` consumer argument, the `x-consumer-timeout` queue argument, the `consumer-timeout` policy key, or the global `consumer_timeout` setting in `rabbitmq.conf`. The default remains 30 minutes.

Deployments that relied on classic queues never timing out unacknowledged deliveries (the `4.3.x` behaviour) should set `consumer_timeout` to a suitable value, or use a policy or queue argument, before upgrading.

GitHub issue: [#17037](https://github.com/rabbitmq/rabbitmq-server/pull/17037)

## Upgrading to 4.4.0

### Documentation Guides on Upgrades

See the [Upgrading guide](https://www.rabbitmq.com/docs/upgrade) for documentation on upgrades and [GitHub releases](https://github.com/rabbitmq/rabbitmq-server/releases) for release notes of individual releases.

This release series supports upgrades from `4.3.x`. Upgrades from earlier series are **not** supported: users must upgrade to the latest available `4.3.x` patch release before upgrading to `4.4.0`.


### New Required Feature Flags

All feature flags introduced in `4.3.0` and earlier are required, including the following:

 * `rabbitmq_4.3.0`
 * `rabbitmq_4.2.0`
 * `rabbitmq_4.1.0`
 * `rabbitmq_4.0.0`

Enable all required feature flags before upgrading to `4.4.0`.


### Mixed Version Cluster Compatibility

RabbitMQ 4.4.0 nodes can run alongside `4.3.x` in the same cluster.

Mixed version clusters are a mechanism that allows rolling upgrades and are not meant to be run for extended periods of time (no more than a few hours).

Classic queue consumer timeout is gated by the `rabbitmq_4.4.0` feature flag. While the flag is disabled (that is, during a rolling upgrade before it has been enabled cluster-wide), classic queues use the default 30-minute consumer timeout rather than a value configured via `consumer_timeout`, the `consumer-timeout` policy key, or the `x-consumer-timeout` argument. The configured value takes effect once `rabbitmq_4.4.0` is enabled on all nodes.


### Recommended Post-upgrade Procedures

Enable the `rabbitmq_4.4.0` feature flag once all nodes have been upgraded so that classic queues honour the configured consumer timeout.

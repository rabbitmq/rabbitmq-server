## RabbitMQ 4.4.0

RabbitMQ `4.4.0` is a new feature release.

## Breaking Changes and Compatibility Notes

 * The following AMQP 0-9-1 headers are no longer parsed:

   ```
   x-amqp-1.0-properties
   x-amqp-1.0-app-properties
   x-amqp-1.0-message-annotations
   x-amqp-1.0-footer
   ```

   RabbitMQ 3.13 and earlier used them to carry the AMQP 1.0 sections of a
   message received over AMQP 1.0. Nothing has written them since 4.0, so only
   a message stored by a 3.13 or earlier node and not read since carries them.
   Such a message is still delivered, with these headers converted like any
   other `x-` header rather than restored as AMQP 1.0 sections.

 * Likewise, the `x-basic-delivery-mode`, `x-basic-priority` and
   `x-basic-expiration` message annotations are no longer parsed. They were
   written before 4.0 when an AMQP 0-9-1 message was encoded as AMQP 1.0 for a
   stream, so only a stream entry written by a 3.13 or earlier node carries
   them, and reading it no longer restores those three properties.

 * OpenID Connect discovery responses are now validated more strictly. A
   deployment whose identity provider serves non-HTTPS (`http://`) endpoints,
   or whose `issuer` claim does not match the discovery endpoint used to
   retrieve it, will fail discovery validation after the upgrade. 

   This is known to affect Cloud Foundry UAA, whose issuer is its token endpoint URL
   rather than a prefix of its discovery endpoint.

   Set `auth_oauth2.discovery.verify_issuer` and/or
   `auth_oauth2.discovery.verify_https_endpoints` to `false` before upgrading
   installations with non-compliant IdPs such as Cloud Foundry UAA.

   See [Discovery Payload Validation](https://www.rabbitmq.com/docs/oauth2#discovery-payload-validation)
   for details on validation rules and configuration options.

 * `GET /api/auth/hash_password/{password}` was replaced with another endpoint, `POST /api/auth/hash_password`. 
    The new endpoint consumes a POST body with JSON document with one key `{"password": "..."}`


## Changes Worth Mentioning

### Core Server

#### Enhancements

 * Quorum queues now support delayed messages.
 
   A message with an `x-opt-delivery-time` annotation or header set to a future time,
   in milliseconds since the Unix epoch, will be routed and delivered at that time and not
   immediately.

   AMQP 1.0 clients set it as a message annotation, AMQP 0-9-1 clients as a
   `long` header.

   An AMQP 1.0 consumer can also delay redelivery of a message by setting
   `x-opt-delivery-time` in the annotations of a `modified` outcome.

   GitHub issue: [#16583](https://github.com/rabbitmq/rabbitmq-server/pull/16583)

 * AMQP 1.0 clients can now request sole (exclusive) ownership of a container ID. 

   In case of a conflict, the server either refuses the new connection or closes the existing one,
   depending on what the client requested, per the [AMQP 1.0 Connection Uniqueness](https://docs.oasis-open.org/amqp/soleconn/v1.0/soleconn-v1.0.html)
   protocol extension.

   GitHub issue: [#16669](https://github.com/rabbitmq/rabbitmq-server/pull/16669)

 * A new, optional `x-name-prefix` queue argument sets the prefix used for a server-named
   queue's generated name, capped at 64 bytes. The default prefix remains
   `amq.gen`.
 
   This feature is specific to AMQP 0-9-1.

   GitHub issue: [#16233](https://github.com/rabbitmq/rabbitmq-server/pull/16233)

 * The classic queue shared message store gained a new v2 on-disk file format (`.sqs`).
   New files are written in v2 automatically. Existing v1 files (`.rdq`) are left as-is.

   Note that a node with v2 files present cannot be downgraded to `4.3.x` or earlier.

   GitHub issue: [#17166](https://github.com/rabbitmq/rabbitmq-server/pull/17166)

 * A stream can now start at an offset other than `0`, set with the new
   `x-stream-initial-offset` optional queue argument. While the stream is empty,
   the `first` and `next` offset specifications resolve to this offset. The stream
   protocol accepts the same value as the `stream-initial-offset` argument of the
   `Create` command.

   The initial offset is fixed when the stream is created, so there is no policy
   for it, and redeclaring the stream with a different value is rejected.

   GitHub issue: [#17300](https://github.com/rabbitmq/rabbitmq-server/pull/17300)

 * Multiple stream coordinator efficiency improvements.

   For example, the stream coordinator now retries failed stream member actions sooner, with
   keeping a related stream partition process blocked for the retry delay.

   Failed operations are now retried after a short randomised delay, and actions that
   failed because a node was down are retried when that node comes back.

   GitHub issue: [#16515](https://github.com/rabbitmq/rabbitmq-server/pull/16515)

 * PBKDF2-HMAC-SHA256 now can be used for password hashing:

   ```ini
   password_hashing_module = rabbit_password_hashing_pbkdf2_sha256
   ```

   GitHub issue: [#17316](https://github.com/rabbitmq/rabbitmq-server/pull/17316)

 * AMQP listeners can now bind to a Unix domain socket, using the same `listeners.tcp.*`
   settings as a TCP listener:

   ```ini
   listeners.tcp.1 = unix:/var/run/rabbitmq/rabbitmq.sock:0
   ```

   Contributed by @Piyush0049.

   GitHub issue: [#16963](https://github.com/rabbitmq/rabbitmq-server/pull/16963)

#### Bug Fixes

 * The stream coordinator could leave a stream without a writer and never recover it,
   keep a stale `start` action after a leader election, or leave a replica
   disconnected after its node came back.

   GitHub issue: [#16515](https://github.com/rabbitmq/rabbitmq-server/pull/16515)

 
### CLI Tools

#### Enhancements

 * Two new commands, `rabbitmqctl sole_connection_status` and
   `rabbitmqctl sole_connection_force_delete`, inspect and manage AMQP 1.0 sole connections.

   GitHub issue: [#16669](https://github.com/rabbitmq/rabbitmq-server/pull/16669)

 
### Management Plugin

#### Enhancements

 * A new endpoint, `GET /api/init`, cuts the number of blocking requests the UI
   has to make with certain authentication and login flows.

   GitHub issue: [#17287](https://github.com/rabbitmq/rabbitmq-server/pull/17287)

### STOMP Plugin

#### Enhancements

 * Following the footsteps of AMQP 1.0 and MQTT in previous years,
   the STOMP is now a standardlone protocol, that is, it is no longer built on AMQP 0-9-1.

   GitHub issue: [#9141](https://github.com/rabbitmq/rabbitmq-server/pull/9141)

 
### Auth Backend OAuth 2 Plugin

#### Enhancements

 * OpenID Connect discovery responses fetched from identity providers are now
   validated according to OpenID Connect Discovery 1.0 spec seciton §4.3. See
   [Discovery Payload Validation](https://www.rabbitmq.com/docs/oauth2#discovery-payload-validation)
   for details on validation rules and configuration options.

   GitHub issue: [#17363](https://github.com/rabbitmq/rabbitmq-server/pull/17363)

### Erlang AMQP 0-9-1 Client

#### Enhancements

 * The `auth_mechanism` query parameter of an AMQP 0-9-1 URI is now restricted to
   the mechanisms the client actually supports (`plain`, `amqplain`, `external`,
   `crdemo`), and an unsupported value is now rejected when the URI is parsed
   rather than when the connection is established. This also applies to the
   Shovel and federation plugins, which parse URIs the same way.

 * Likewise, the `verify` query parameter of an AMQP 0-9-1 URI now only accepts
   `verify_peer` or `verify_none`, and an unsupported value is rejected when the
   URI is parsed rather than when the TLS connection is established.

### Erlang AMQP 1.0 Client

#### Enhancements

 * Connection configuration now accepts a `connect_timeout`, applied to the socket
   connect and, for TLS, to the handshake as well. Without it, a peer that accepts the
   TCP connection and then stops responding blocks `amqp10_client_sup` indefinitely,
   which in turn blocks every other connection attempt in the node.
   Defaults are unchanged: `infinity` for TCP and TLS, 5000 ms for WebSockets.

 * A direct connection opened while a *different* cluster node had a resource
   alarm was not blocked. A resource alarm blocks publishers cluster-wide,
   but a newly registered connection was only told about alarms on its own
   node, so it kept publishing at full rate. Direct connections are used by
   the federation and shovel plugins, the HTTP API endpoints that publish and
   get messages, and the tracing plugin, so this is an observable change for
   them during an alarm on a peer node.

### Federation Plugin

#### Bug Fixes

 * Federation links now respect resource alarms on the downstream node. A link
   registers for `connection.blocked` on its downstream connection and buffers
   deliveries while an alarm is active, forwarding them in publish order once
   it clears. Links also publish through credit flow, so a backed-up
   downstream queue can throttle a link before conditions escalate into an
   alarm. Previously a link kept publishing at full rate into a node that had
   already run out of memory or disk space.

   With `ack-mode` set to `no-ack` the buffer is not bounded, because there is
   no upstream acknowledgement to withhold, and the same is true in any ack
   mode if `prefetch-count` is set to 0, which means unlimited. This matches
   the behaviour of the AMQP 0-9-1 shovel.

   A link that is holding buffered deliveries when its downstream channel goes
   away now restarts rather than continuing with a buffer it can neither
   forward nor drain. In every ack mode but `no-ack` the upstream still holds
   those deliveries unacknowledged and redelivers them to the restarted link;
   with `no-ack` they are lost, because the upstream did not keep a copy.

   Contributed by @Vishal-770.

   GitHub issue: [#16670](https://github.com/rabbitmq/rabbitmq-server/issues/16670)

### Dependency Changes

 * `osiris` was upgraded to [`1.14.0`](https://github.com/rabbitmq/osiris/releases)
 * `ra` was upgraded to [`3.2.0`](https://github.com/rabbitmq/ra/releases)
 * `khepri` was upgraded to [`0.19.1`](https://github.com/rabbitmq/khepri/releases/tag/v0.19.1)
 * `thoas` was dropped: JSON encoding and decoding now uses the Erlang/OTP `json` module
